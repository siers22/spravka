# Проверка примеров .NET и SQL

Дата: 3 октября 2026 года.

Проверены `examples/ExamGuide`, `examples/ShoeStore`, SQL обоих диалектов и соответствующие скачиваемые архивы. Код уроков импортируется из этих же файлов через `?raw`.

## Вывод

Оба приложения работоспособны в основных учебных сценариях с PostgreSQL. Сборка C# и Razor проходит без предупреждений. Схемы, исходные данные, импорт, вход, API, каталог и оформление заказа проверены исполнением. Найдены три воспроизводимые проблемы: SQL скидки не самодостаточен для SQL-редактора и два граничных случая возвращают HTTP 500.

SQL Server проверен статически; работа приложения с настоящим SQL Server и публикация/запуск на Windows не проверены. Проверка не является нагрузочным тестом или аудитом безопасности.

## Найденные проблемы

### 1. P2 — SQL скидки нельзя выполнить напрямую в pgAdmin/SSMS

Файлы: [postgres-discount.sql](../examples/ShoeStore/sql/postgres-discount.sql), [mssql-discount.sql](../examples/ShoeStore/sql/mssql-discount.sql), строка 9.

Оба файла используют `@previousMonthStart` и `@currentMonthStart`, но не содержат способа задать эти значения при самостоятельном запуске. Комментарий говорит о передаче параметров, однако учебный файл не содержит исполняемого примера для SQL-редактора.

Воспроизведение PostgreSQL: выполнить неизменённый `postgres-discount.sql` в базе после импорта. Получено `ERROR: column "previousmonthstart" does not exist`. Этот же файл работает через Npgsql при добавлении двух параметров; результат совпал с ценами C#-каталога для всех 31 моделей. Следовательно, ошибка касается самостоятельного запуска учебного SQL, а алгоритм скидки в приложении работает.

Для SQL Server ожидается ошибка необъявленной переменной: в файле отсутствует `DECLARE`. Это вывод из текста скрипта и [документации Microsoft о переменных T-SQL](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/variables-transact-sql?view=sql-server-ver17), а не результат запуска SQL Server. Именованные параметры PostgreSQL переписывает клиентская библиотека, что описано в [документации Npgsql](https://www.npgsql.org/doc/basic-usage.html).

Рекомендация: дать самостоятельный SQL с датами в CTE для PostgreSQL и `DECLARE` для SQL Server либо отдельный полный пример выполнения через ADO.NET. Даты для проверки апреля: 2026-04-01 и 2026-05-01.

### 2. P2 — пустой Puzzle ломает обработку формы входа

Файл: [Login.cshtml.cs](../examples/ExamGuide/Pages/Login.cshtml.cs), строки 39–45.

При POST с непустыми логином и паролем, действующими cookie/antiforgery и `Puzzle=` MVC связывает пустое значение с `null`. `JsonSerializer.Deserialize<int[]>(Puzzle)` выбрасывает `ArgumentNullException`; обработчик перехватывает только `JsonException`. Результат — HTTP 500 вместо сообщения о неверном пазле.

Воспроизведено с логином `nobody`, паролем `test`: `Puzzle=` → 500; `Puzzle=null` и `Puzzle={bad` → 200 с обработанной ошибкой. Логин выбран несуществующий, чтобы не блокировать аккаунты тестом.

Рекомендация: явно проверить пустое/отсутствующее поле перед десериализацией и направить его в обычную ветку неверного пазла. Основной вход при правильно собранном пазле работает.

### 3. P3 — несуществующий заказ и неверная дата дают HTTP 500

Файл: [Details.cshtml.cs](../examples/ShoeStore/Pages/Orders/Details.cshtml.cs), строки 20–24; [Details.cshtml](../examples/ShoeStore/Pages/Orders/Details.cshtml), строки 3–4.

В ветке ошибки даты результат `OnGetAsync(id)` игнорируется. Если заказ отсутствует, загрузка возвращает `NotFound()`, но обработчик всё равно возвращает `Page()`. Razor обращается к `Model.Order`, который равен `null`.

Воспроизведение от имени Admin: POST `/Orders/Details?handler=Date`, `id=2147483647`, `date=invalid`, действующий antiforgery → 500. Та же неверная дата для существующего заказа `id=1` → 200 с сообщением. Сценарий также возможен, если заказ удалили после открытия формы, а затем отправили пустую/некорректную дату.

Рекомендация: вернуть результат загрузки, если заказ отсутствует; отрисовывать форму ошибки только при загруженном заказе.

## Статическая проверка SQL Server и ограничения

Схемы, данные и расчёты обоих диалектов совпадают после нормализации `nvarchar`/`varchar`, Unicode-префиксов строк и `BEGIN TRANSACTION`/`BEGIN`. SQL Server использует Unicode-поля и литералы. C# вызывает оба провайдера через ADO.NET, параметры передаются отдельно от текста SQL. Эти проверки не заменяют выполнение на SQL Server.

Чистое восстановление NuGet из Интернета не проверялось: сборка использовала ранее восстановленные пакеты, тестовый проект восстановлен из локального кэша. Для запуска по README нужны SDK, доступные пакеты, созданная БД и исправленная строка подключения с собственным паролем/экземпляром.

Параллельные оформления заказов и одновременное выделение ID через `MAX(id)+1` не тестировались. Serializable-транзакции могут завершаться конфликтом; автоматического повтора в коде нет. Это ограничение для многопользовательской эксплуатации, а не воспроизведённая ошибка текущей проверки.

Исходники приложений и SQL не исправлялись в рамках проверки. Временные приложения и PostgreSQL после проверки остановлены.
